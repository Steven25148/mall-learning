# 后端接口条件开发闭环练习

## 练习名称

为后台订单列表增加“实付金额区间”筛选。

## 练习目标

独立完成一次真实的小需求闭环：

> 理解需求 → 定位调用链 → 设计参数 → 修改代码 → 验证参数 → 验证 SQL → 主动找错并修复 → 自查差异 → 提交 Git commit

完成后，你应当能用自己的话解释下面这条实际调用链：

```text
GET /order/list
  → OmsOrderController.list
  → OmsOrderService.list
  → OmsOrderServiceImpl.list
  → OmsOrderDao.getList
  → resources/dao/OmsOrderDao.xml#getList
  → oms_order.pay_amount
```

## 需求卡

在现有后台订单列表接口 `GET /order/list` 中增加两个可选查询参数：

| 参数 | 类型 | 是否必填 | 含义 |
| --- | --- | --- | --- |
| `minPayAmount` | decimal | 否 | 最低实付金额，包含边界 |
| `maxPayAmount` | decimal | 否 | 最高实付金额，包含边界 |

业务规则：

1. 两个参数都不传时，接口行为必须和修改前一致。
2. 只传 `minPayAmount` 时，查询 `pay_amount >= minPayAmount` 的订单。
3. 只传 `maxPayAmount` 时，查询 `pay_amount <= maxPayAmount` 的订单。
4. 两个参数都传时，查询闭区间 `[minPayAmount, maxPayAmount]`。
5. 金额不能小于 0，最多保留两位小数。
6. 同时传入两个参数时，最低金额不能大于最高金额。
7. 参数不合法时，必须在进入数据库查询前返回参数校验失败。
8. 原有订单号、状态、来源、类型、日期、收货人条件以及分页功能不能失效。

本次不修改数据库结构，不增加新接口，不修改返回结构，不改前端。

## 验收示例

以下示例省略域名、登录 Token 和其他已有参数：

| 请求 | 预期 |
| --- | --- |
| `/order/list` | 与修改前结果一致 |
| `/order/list?minPayAmount=100` | 每条结果的 `payAmount >= 100` |
| `/order/list?maxPayAmount=200` | 每条结果的 `payAmount <= 200` |
| `/order/list?minPayAmount=100&maxPayAmount=200` | 每条结果的 `payAmount` 在 100 到 200 之间，包含边界 |
| `/order/list?minPayAmount=100&maxPayAmount=100` | 合法，只返回金额等于 100 的订单 |
| `/order/list?minPayAmount=-1` | 参数校验失败，不能执行订单查询 SQL |
| `/order/list?maxPayAmount=1.234` | 参数校验失败 |
| `/order/list?minPayAmount=200&maxPayAmount=100` | 参数校验失败，不能执行订单查询 SQL |
| `/order/list?minPayAmount=abc` | 参数类型转换失败；记录实际响应并解释由哪个环节产生 |

## 第二关：先写修改计划

不要马上敲代码。先写出预计改动的文件、每个文件的职责和“不需要修改”的文件。

## 第五关：主动找错

必须完成一次“失败 → 定位 → 修复 → 回归”，不能只测成功路径。

优先使用下面这个真实且常见的排错场景：

1. 请求 `minPayAmount=-1`。
2. 如果接口仍然返回正常订单列表，先不要改 SQL。
3. 从请求绑定过程向下追踪：DTO 上虽然有约束，Controller 是否真的触发了校验？
4. 找到原因后修复。
5. 再次请求同一参数，确认返回参数校验失败。
6. 查看日志，确认修复后非法请求没有进入 `OmsOrderDao.getList`。
7. 再回归一个合法金额区间，确认修复没有误伤正常查询。

如果这个问题第一次就没有出现，则从以下项目中主动选择一个进行故障验证：

- 暂时把 XML 中的属性名写错，观察异常信息能否指向参数对象属性。
- 暂时将上限条件误写成下限条件，使用只传上限的用例发现结果错误。
- 暂时将闭区间写成开区间，准备一条边界金额数据发现错误。

故障验证完成后必须恢复正确实现，禁止把故障代码提交。

## 分级提示

只有卡住时才向下看，一次只看一级。

### 提示 1：定位方向

金额参数属于现有查询对象。列表查询最后调用的是自定义 DAO 的 XML，不是生成 Mapper 的 `selectByExample`。

### 提示 2：类型与约束方向

查看 `oms_order.pay_amount` 的 SQL 类型，再比较 `OmsOrder` 中该字段的 Java 类型。Bean Validation 中有用于十进制下限和整数位/小数位限制的约束。

### 提示 3：跨字段方向

单个字段注解只能判断一个值。区间顺序需要一个能同时看到两个字段的规则。对于这次小练习，可以在查询 DTO 中提供一个用于校验的布尔方法；也可以实现类级约束，但后者工作量更大。

### 提示 4：Controller 方向

本项目其他 Controller 已经展示了如何让 Spring 对入参执行校验。搜索 `@Validated`，比较请求体参数与普通查询对象的用法。

### 提示 5：XML 方向

两个边界都是可选的，因此通常需要两个独立的 `<if>`。参数由 `@Param("queryParam")` 包裹，XML 访问字段时要带此前缀。
